## 二、第一版使用範圍

**只有 C（自主挑戰）與 D（學習與技能）開放 AI 建議。**

這不是「A／B 類的孩子比較危險」。是這兩類任務的建議天然落在**實體家務操作**上，
而那正好是內容安全層最弱的地方。閱讀計畫、運動練習、學校作業的建議
落在時間、範圍與文字表達上 —— 就算模型胡說，最壞的結果是一句不合適的文案，
不是一個危險的動作。

六種 Demo 任務的實際落點：

| 任務 | 分類 | 結果 |
|------|------|------|
| 完成學校作業 | D · 單次 | 開放 |
| 運動練習 | D · 週期 | 開放 |
| 每週閱讀計畫 | D · 成長計畫 | 開放 |
| 餐後整理 | B · 家庭參與 | **不開放** |
| 整理書包 14 天 | A · 生活常規 | **不開放** |
| 每週餐桌小幫手 | B · 家庭角色 | **不開放** |

一半的 Demo 任務拿不到 AI 建議。這是刻意的，也是這一輪最主要的安全措施。

**放寬的前提**（三項都要滿足，不是任選）：

1. 內容安全層在 A／B 類語料上做過一輪真實模型 red-team，且有量化攔截率
2. 付費方案已開通，配額不再是限制因素
3. 有真實家長使用資料可以判斷「AI 對家務類任務的建議是否真的有用」

在那之前不要因為「使用者反映家務任務也想要建議」就直接放寬。

## 三、伺服器限流

**表**：`public.task_ai_rate_limit_counters`
**函式**：`public.consume_task_ai_recommendation_quota_v1(integer, integer)`

設計要點：

- 身分一律取自 `auth.uid()`，**不接受 client 傳入的 user_id**
- 檢查與遞增在**同一個 transaction**：`ON CONFLICT DO UPDATE ... RETURNING` 取得 row lock，並行呼叫者排隊而不是各讀各的
- 超額時把剛才的 +1 **退回**，否則「被擋」本身會延長封鎖時間
- 回應**不含目前用量或上限**，只有 `retry_after_seconds`
- RLS 啟用且**沒有任何 policy** —— 這張表沒有合法的直接讀寫情境
- 限流查不動時**不放行**（fail-closed）

已在 staging 驗證的權限狀態：

```
table exists      : yes
RLS enabled       : yes
policies          : 0
SECURITY DEFINER  : yes
authenticated 可 EXECUTE 函式 : yes
authenticated 可 SELECT 表    : no
```

### ⚠️ 目前的數字是暫定值

| 設定 | staging 現值 | 依據 |
|------|-------------|------|
| `TASK_AI_RATE_LIMIT_PER_10MIN` | 6 | 直覺推估，未經產品驗證 |
| `TASK_AI_RATE_LIMIT_PER_DAY` | 10 | 遷就免費配額，**不是產品決策** |
| 契約後備值 | 6 / 40 | env 沒設定時的保守值 |

這些數字沒有使用資料支撐。**不要把它們寫進對外文件或當成正式政策。**
真實值要等有人真的用過才知道 —— 一個家長在一次任務編輯裡合理會按幾次，
目前沒有人知道。

程式裡**沒有**硬編 Gemini 的每日配額。那個數字屬於帳戶方案，
寫進來只會在方案改變時變成一個沒有人記得的謊言。

## 四、總開關

`TASK_AI_ENABLED`。`supabase secrets set` 幾秒生效，不需要 redeploy。

- 沒設定 = **開啟**（既有部署不會因為少一個變數就整個功能消失）
- 設成 `false` / `0` / `off` / `disabled` = 關閉
- **設了但看不懂（例如 `flase`）= 關閉**

最後一條的不對稱是刻意的：沒設定代表沒有人表達意見，
設成 `flase` 代表有人正在試圖關掉它，而猜錯的代價不對等。

關閉時回 HTTP 200 + `unavailable / SERVICE_DISABLED`，**在 auth 之前就返回** ——
一個還要先打一次 GoTrue 的 kill switch 是個很差的 kill switch。

## 五、延遲：量到了，但沒有解決

在 staging 上對最重的任務（`reading-plan`，成長計畫、欄位最多、輸出最長）
連續量測 6 次，`TASK_AI_TIMEOUT_MS=20000`：

| # | 結果 | 延遲 |
|---|------|------|
| 1 | SERVICE_ERROR | 3,484ms |
| 2 | suggestions | 12,344ms |
| 3 | **TIMEOUT** | 20,715ms |
| 4 | suggestions | 16,430ms |
| 5 | suggestions | 17,445ms |
| 6 | suggestions | 7,960ms |

換算成三個候選逾時值：

| 逾時 | 6 次中成功 |
|------|-----------|
| 12,000ms | 1 |
| 16,000ms | 2 |
| 20,000ms | 4 |

**結論與誠實的限制：**

- 12 秒對成長計畫類任務**不可用** —— 六次裡只有一次來得及
- 20 秒仍有失敗（#3 超過 20.7 秒）
- 可用樣本只有 4 筆。**這個數量算不出百分位數**，腳本因此拒絕輸出 p95；
  任何「p95 是 X」的說法目前都沒有依據
- #1 的 SERVICE_ERROR 在 3.5 秒回來，那不是逾時。它是 429 還是 5xx
  **只有 Dashboard 的 log 看得出來**，而我沒有 Dashboard 存取權，
  所以這一筆的成因目前不明

**沒有把逾時拉到 30 秒**，因為那不是解法：家長等 30 秒仍然是壞體驗，
而且只是把失敗換成更長的等待。真正的成因是輸出太長。
這一輪已經把 prompt 要求從 5 條降到 3 條；下一步的候選是縮短 rationale 上限、
或改成串流回應。**這件事沒有在這一輪解決。**

## 六、內容安全：改善了，但沒有解決

B2A 的 red-team 顯示：關鍵字層擋得住「清理瓦斯爐」，擋不住
「把煮東西的檯面擦乾淨，包含上面那圈金屬架」。5 種同義說法有 4 種通過。

這一輪的處置是**共現片語**而不是加寬泛詞：要同時出現「加熱動作」與「那個東西」
才算命中。理由是，加入「廚房」「爐子」「檯面」這種寬泛詞會擋掉
「幫忙擦餐桌」「整理書架」這類核心任務，然後有人把整層關掉 ——
一個被關掉的安全層擋不住任何東西。

本機驗證結果：

- B2A 漏掉的 4 種同義說法：**全部擋下**
- 安全對照組 6 項（洗鍋子／書架／擦餐桌／收碗筷／金屬水壺／廚房一般協助）：**全部放行**

### 這一節必須保留的三句話

1. **這不是完整的語意安全證明。** 它是一組人工寫的規則，不是模型理解。
2. **不能宣稱所有同義詞都能被攔截。** 第五種說法仍然會漏，而且我們不知道它長什麼樣。
3. **真實模型 red-team 仍需持續進行。** 這一輪沒有跑新的 red-team（配額用在 E2E 與延遲量測上）。

真正的第一道防線不是這些規則，是第二節的使用範圍限縮。

## 九、驗證這些說法的方式

```bash
# 契約與型別（jest，App 端）
npx jest src/screens/parent/tablet/taskDrawer/taskAi

# Edge 端全部（Deno）
cd supabase/functions/task-ai-recommendation
deno test --frozen --allow-env --allow-net --allow-read tests/

# staging 協定檢查（不消耗模型呼叫）
deno run --allow-env --allow-net --allow-read --allow-write \
  scripts/liveCheck.ts --mode=protocol --out=<repo 外的資料夾>
```

`scripts/liveCheck.ts` 有**跨次數累計的每日預算**（`TASK_AI_MAX_LIVE_TEST_CALLS`），
重跑不會從零開始。它也在送出任何請求前比對 project ref，對到 production 直接結束。
